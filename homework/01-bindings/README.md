## Зачем мы это делаем

В Python-проекте не весь код обязательно написан на Python. Например, вычислительное

Знакомство с pybind11 и CMake заранее не требуется: сначала разберите готовый
пример, затем используйте подсказки ниже и ссылки на документацию.

## Введение: что такое биндинги

Биндинг делает функцию из одного языка вызываемой из другого. В нашем случае
Python вызывает C++ через модуль расширения. pybind11 описывает доступные функции,
преобразует аргументы и связывает исключения C++ с исключениями Python.

Путь от исходника до вызова:

```text
C++ → компилятор → модуль _core → wheel → pip install → import tensor_ops
```

Роли файлов и инструментов:

- `PYBIND11_MODULE(_core, ...)` задаёт модуль; `module.def(...)` экспортирует функцию.
- `__init__.py` предоставляет удобный публичный API, например `tensor_ops.mac`.
- `CMakeLists.txt` задаёт исходники, стандарт C++ и место установки расширения.
- `pyproject.toml` описывает build backend, build-зависимости и runtime-зависимости.
- `scikit-build-core` связывает стандартную Python-сборку с CMake.
- Wheel содержит уже собранный код. Пользователю не нужно вручную компилировать `.so`.

Зависимости **сборки** и **исполнения** различаются. Компилятор, CMake и pybind11
нужны для сборки. NumPy нужен нашему API при исполнении; его необходимо объявить
в metadata пакета. pytest нужен проверяющему, но не пользователю функции.

### Три имени, которые легко перепутать

| Имя | Где используется |
|---|---|
| `mlops-tensor-ops` | Имя дистрибутива в `pyproject.toml` и командах `pip show` |
| `tensor_ops` | Имя Python-пакета: `from tensor_ops import mac` |
| `_core` | Имя скомпилированного модуля внутри пакета: `tensor_ops._core` |

В заготовке `__init__.py` уже импортирует `mac` из `._core`. Поэтому CMake должен
установить расширение именно внутрь `tensor_ops`, а `PYBIND11_MODULE` и target CMake
должны согласованно называть модуль `_core`. Wheel — устанавливаемый архив;
sdist — архив исходников, из которого ещё предстоит собрать wheel.

### Массивы на границе Python / C++

NumPy-массив — это буфер с числами и описание того, как эти числа читать.
Указатель C++ сам по себе такого описания не содержит.

| Свойство | Что означает | Зачем проверять в ДЗ |
|---|---|---|
| `dtype` | Тип элемента и порядок байтов | Ядро читает `double`, а не `float32` или целые числа |
| `ndim`, `shape` | Число осей и их размеры | Нужны три оси и одинаковые формы всех входов |
| `strides` | Шаг в байтах при движении по каждой оси | Срез может пропускать элементы исходного буфера |
| `C_CONTIGUOUS` | Данные расположены непрерывно в C-порядке | Можно обойти элементы одним плоским циклом |
| `ALIGNED` | Данные выровнены для своего типа | Выравнивание нужно для безопасного доступа через типизированный указатель |
| `WRITEABLE` | Разрешено ли изменять массив | Вход только читаем: read-only массив тоже допустим |

Запустите этот фрагмент в Python после подготовки env:

```python
import numpy as np

x = np.arange(24, dtype=np.float64).reshape(2, 3, 4)
view = x[:, :, ::2]
packed = view.copy(order="C")

for name, value in [("x", x), ("view", view), ("packed", packed)]:
    print(name, value.shape, value.strides, value.flags.c_contiguous)

assert view.shape == packed.shape
assert np.array_equal(view, packed)
assert not view.flags.c_contiguous
assert packed.flags.c_contiguous
```

У `view` и `packed` одинаковые значения и форма `(2, 3, 2)`, но последний шаг
в памяти равен 16 и 8 байтам соответственно. Чтение `view` как непрерывной
последовательности `double` дало бы не те элементы. Поэтому внутри биндинга сначала
проверяем свойства массива и только затем обращаемся к данным.

Для массива формы `(d0, d1, d2)` в C-порядке индекс `(i, j, k)` соответствует
плоскому индексу `(i * d1 + j) * d2 + k`. Если все входы имеют одинаковую форму
и удовлетворяют контракту памяти, ядру достаточно числа элементов `N` и указателей;
три вложенных цикла не обязательны.

Для этого ДЗ ограничиваем вход непрерывными, выровненными массивами. Подготовить
подходящий вход явно, **до вызова** функции, можно так:

```python
ready = np.require(view, dtype=np.float64, requirements=["C", "A"])
```

Внутри биндинга не нужно молча менять dtype или копировать неподходящий вход.
Иначе вызывающий код не узнает о нарушении контракта. `np.require` выше — явная
подготовка данных пользователем функции, а не часть реализации `mac`.

### Подсказки по pybind11

| Задача | API / подсказка |
|---|---|
| Принять NumPy-массив без заранее выбранного dtype | `const py::array&`, как в заготовке |
| Запретить преобразование аргумента при вызове | `py::arg("a").noconvert()`; правило нужно для каждого входа |
| Сравнить dtype с типом `double` | `value.dtype().equal(py::dtype::of<double>())` |
| Проверить размерность и размеры осей | `value.ndim()`, `value.shape(axis)`; одного сравнения `size()` недостаточно |
| Проверить C-порядок и выравнивание | Флаг `py::array::c_style` в `value.flags()` и `value.attr("flags").attr("aligned").cast<bool>()` |
| Создать выход с собственным буфером | `py::array_t<double>` с нужной формой; заполнить все элементы перед возвратом |
| Получить данные | `data()` для чтения, `mutable_data()` для записи в новый выход |
| Сообщить о нарушении контракта | `throw py::type_error(...)` или `throw py::value_error(...)` |

**Равенство dtype — не идентичность объектов.** Не используйте `.is(...)` вместо
`.equal(...)`: два разных объекта могут описывать один и тот же тип. Например,
`np.dtype("float64", copy=True)` по-прежнему задаёт допустимый dtype. Native-endian
означает привычный для текущей машины порядок байтов; одного размера элемента
в 8 байт недостаточно для проверки типа и порядка байтов.

Не переносите из примеров документации `forcecast` без разбора: он допускает
преобразование неподходящих массивов, а наше условие требует их отклонять.
Подробности — в [документации pybind11 по массивам](https://pybind11.readthedocs.io/en/stable/advanced/pycpp/numpy.html).

После валидации всех трёх входов можно привести указатели к `const double*` и
передать их ядру. `const` запрещает запись через этот указатель, но **не проверяет**
dtype, форму или размещение данных. Для результата создайте новый NumPy-массив:
не возвращайте указатель на локальный C++-массив, память которого исчезнет при выходе
из функции. При `N == 0` возвращайте пустой результат нужной формы без разыменования
указателей, но не пропускайте проверку входов.

Все Python-объекты в основной версии обрабатывайте под GIL — блокировкой доступа
к Python-интерпретатору. Управлять её освобождением для этого ДЗ не требуется.

## Контракт `tensor_ops.mac(a, b, c)`

Для каждого индекса `i, j, k` результат равен `a[i,j,k] * b[i,j,k] + c[i,j,k]`.
Это **поэлементное умножение, не матричное**, broadcasting запрещён.

| Свойство | Требование |
|---|---|
| Входы | Три `numpy.ndarray`, dtype — native-endian `float64` |
| Размерность | Ровно 3 оси; формы всех трёх массивов совпадают |
| Память | `C_CONTIGUOUS` и `ALIGNED`; входы могут быть read-only |
| Выход | Новый C-contiguous `float64`-массив той же формы |
| Изменение данных | Входы не меняются; выход не делит с ними память |
| Пустой массив | Допускается нулевая ось; возвращается пустой массив той же формы |
| Список / неверный dtype | `TypeError`, без автоматического преобразования |
| Неверная форма / ndim / layout | `ValueError`, без аварийного завершения Python |
| Точность | Сравнение с NumPy: `rtol=1e-12`, `atol=1e-12` |

Обязательные численные проверки используют конечные значения умеренной величины,
без переполнения. NaN/inf и поведение при переполнении не входят в обязательную
часть. Форма, dtype и layout проверяются и для пустых входов. Если несколько условий
нарушены одновременно, порядок сообщений об ошибке не оценивается.

## Сдача и оценивание

1. Сделайте fork репозитория [ekolodin/mlops](https://github.com/ekolodin/mlops)
   и клонируйте его на свой компьютер.
2. Создайте ветку `hw01` от `main`: `git switch -c hw01`.
3. Выполните задание в `homework/01-bindings/`. Не изменяйте выданные `tests/`,
   учебный `example/` и файлы других тем. Свои тесты добавляйте в `student_tests/`.
4. Закоммитьте решение и отправьте ветку в свой fork: `git push -u origin hw01`.
5. Откройте Pull Request **в репозиторий курса**, указав:

   - **base repository:** `ekolodin/mlops`, **base:** `main`;
   - **head repository:** ваш fork, **compare:** `hw01`;
   - **заголовок:** `HW01: Фамилия Имя, группа`.

6. Добавьте отчёт в описание PR и отправьте его на ревью. Если PR создан как Draft,
   нажмите **Ready for review** после завершения работы.

Ревью у `@ekolodin` запрашивается автоматически через `CODEOWNERS`.
Если запрос не появился, упомяните `@ekolodin` в комментарии к PR.
Сдаваемая работа — ваш PR в репозитории курса, а не PR внутри собственного fork.

В описании PR укажите:

- Команды сборки и запуска из чистого клона.
- Версии Python, компилятора, pybind11, scikit-build-core и NumPy; ОС и архитектуру.
- Имя и SHA-256 проверенного wheel; команды и результат тестов в чистом env.
- Путь импортированного `_core`, вывод `pip check` и список пакетов env получателя.
- Контракт функции, различие build/runtime dependencies и описание пойманной ошибки.
- Использованные источники и ограничения реализации.

Исправления по замечаниям отправляйте в ту же ветку `hw01` — они появятся
в существующем PR. После исправлений оставьте комментарий о готовности к повторной
проверке. Новый PR для исправлений не нужен.

После проверки преподаватель закрывает PR **без слияния в `main`**.
Репозиторий публичный: код и обсуждение PR видны другим студентам.

Wheel, `.so`, env и build-каталоги **не коммитьте**: проверяющий собирает пакет из
исходников.

| Критерий | Баллы |
|---|---:|
| Корректное ядро C++, безопасные границы, отсутствие изменения входов | 2 |
| Python API, валидация, отсутствие неявных преобразований | 3 |
| Metadata и зависимости; сборка из чистых исходников; установка wheel | 3 |
| Чистый env; зависимости из metadata; тесты wheel вне исходников | 3 |

Каждый критерий оценивается отдельно.
